# 评价框架负样本识别优化 — 长期计划

## Context

SocialEval 法学论文评价系统在负样本识别上存在严重不足：AI 对质量较差的论文给分过高，无法有效区分正负样本。经过 v2.49-v2.50.3 五轮迭代，确定了核心瓶颈：

- **问题创新性（权重 0.3）**：前置扣分制有效，负样本可降到 30-60 分
- **分析框架（权重 0.15）**：prompt 1100+ 行，扣分指令被淹没，负样本仍得 85-92 分
- **结论可接受性（权重 0.1）**：prompt 1291 行，扣分指令完全被忽略

根本原因：**prompt 过长导致 AI 注意力稀释**。短 prompt（问题创新性 ~200 行）中的扣分指令有效，长 prompt（分析框架/结论 1100+ 行）中的指令被忽略。

## 目标

### 评分口径

v2.51 的优化目标必须以 v0.16 规程中的 `final_score` 为主分，不再用 legacy `weighted_total` 作为优化或部署判断依据。`weighted_total` 只能作为兼容字段和诊断参考。

```text
base_score = (problem_originality*30 + literature_insight*20 + analytical_framework*15 + logical_coherence*20) / 85
final_score = min(base_score + forward_extension_bonus, conclusion_consensus_ceiling)
# 注：conclusion_consensus_ceiling 为 None 时不应用上限，final_score = base_score + bonus
```

所有批量验证、autoresearch metric、部署门槛和报告汇总均以 `final_score` 统计；同时保留逐维度分数、Stage A 命中率、误报率和多模型 std 作为诊断指标。下表的 v2.50.2 当前值来自既有测试记录，Phase 0 需要先用 `final_score` 重新跑一版基线并更新这些数字。

| 指标 | 当前（v2.50.2） | 最终目标 |
|------|----------------|---------|
| 负样本平均分 | 76.1 | < 65 |
| 正负样本差距 | 15.0 | > 25 |
| 负样本识别率（< 75） | 44% | > 75% |
| 正样本稳定性 | 91.1 | > 85 |

### 工程原则

1. **负面模式定义在 YAML 中，执行约束在代码中**：`negative_patterns`、检测 prompt、字段契约和 ceiling 阈值放在框架配置；代码只负责渲染、校验、聚合和应用上限。
2. **Stage A 结果必须可审计**：负面模式检测的输入、输出、模型名、耗时、命中 pattern、证据和应用上限必须落库或写入测试结果。
3. **不得只靠 Stage B 自觉服从 prompt 约束**：v2.49-v2.50.3 已证明长 prompt 中的规则容易被忽略。Stage A 命中后，最终维度分数必须由代码层执行 `min(stage_b_score, detected_ceiling)`。
4. **先验证检测器，再改变评分**：任何负面模式进入生产评分前，必须先完成 dry-run 检测准确率验证。

## Phase 0：Stage A 检测器 dry-run + 基线切换

### 核心思路

先独立验证短 prompt 负面模式检测器，不改变任何维度分数。目标是确认 Stage A 能稳定识别专家意见中的负面模式，同时不过度误伤正样本。

   - 读取并输出 `final_score` 作为主分

3. 用改造后的脚本对 v2.50.2 重新跑一版 `final_score` 基线，更新目标表中的"当前"数值
4. 新建 `scripts/batch_discrimination_test.py`（Phase 4 使用），从一开始就只基于 `final_score`

## Phase 1：两阶段评分架构

### 核心思路

将目标维度的评分拆分为两次独立的 AI 调用。首批只覆盖 `analytical_framework` 和 `conclusion_consensus`；`problem_originality` 已在 v2.50.2 中验证前置扣分有效，暂不纳入架构改动。

1. **Stage A — 负面模式检测器**（短 prompt，~100 行）
   - 只检查 3-5 个负面模式，返回 pattern_flags + severity
   - 不输出维度分数，只输出命中模式、证据、置信度和建议上限

2. **Stage B — 详细评分**（现有维度 prompt）
   - Stage B 继续按当前维度评分契约输出 `DimensionResult`
   - 可在 prompt 顶部提示 Stage A 检测结果，但不把 prompt 服从作为唯一保障

3. **代码层约束应用**
   - 如果 Stage A 检测到负面模式，代码执行：
     ```python
     final_dimension_score = min(stage_b_score, applied_score_ceiling)
     ```
   - `limit_rule_triggered` 或新增 `negative_pattern_triggered` 必须记录被应用的 pattern
   - 如果 Stage A 未触发，Stage B 分数正常采用

4. **多模型 Stage A 一致性决策规则**
   - **多数触发（≥ 50% 模型命中同一 pattern）**：应用 ceiling，正常压分
   - **少数触发（仅 1 个模型命中，其他未命中）**：不自动压分，标记 `requires_manual_review: true`，Stage B 分数正常采用
   - **全部触发**：应用 ceiling，且 `confidence` 取各模型最高值
   - 理由：避免单模型误判导致正样本被硬压分，同时不放过多数模型一致认定的问题

### 并发策略

采用**方案 B：模型内串行，模型间并发**：

```
模型 A: [Stage A → ceiling 结果] → [Stage B（可注入 Stage A 摘要）] → apply min()
模型 B: [Stage A → ceiling 结果] → [Stage B（可注入 Stage A 摘要）] → apply min()
         ↑ 两个模型并发执行 ↑
```

- 每个模型内部先跑 Stage A，拿到 ceiling 后再跑 Stage B（串行）
- 不同模型之间完全并发，互不等待
- 优势：延迟 = 单模型的 (Stage A + Stage B) 时间，而非所有模型 Stage A 完成后再统一跑 Stage B
- 最终聚合时，按上述多模型一致性规则决定是否应用 ceiling

### 模块职责边界

| 模块 | 职责 | 不做什么 |
|------|------|---------|
| `negative_pattern_detector.py` | 调用 AI 检测负面模式，返回 `NegativePatternResult`（含建议 ceiling、evidence、confidence） | 不执行 `min()`，不修改分数 |
| `concurrent_evaluator.py` | 编排 Stage A → Stage B 调用顺序，汇总多模型结果，执行 `min(stage_b_score, ceiling)` | 不定义 pattern 规则，不做 prompt 渲染 |
| `result_validator.py` | 校验 pattern_id 合法性（是否来自 YAML），校验 ceiling 值范围，填充 `negative_pattern_triggered` 字段 | 不执行 `min()`（由 evaluator 在聚合前完成） |
| `prompt_builder.py` | 渲染 Stage A prompt、可选的 Stage A 摘要注入到 Stage B prompt | 不做检测逻辑，不做分数计算 |

### 具体步骤

1. 创建 `src/evaluation/negative_pattern_detector.py`
   - 为 `analytical_framework` 和 `conclusion_consensus` 各设计一个短 prompt
   - 从专家意见提取 pattern 描述
   - 返回结构化 `NegativePatternResult`

2. 在 YAML 框架配置中新增 `negative_patterns` 区块
   ```yaml
   negative_patterns:
     mode: enforce
     dimensions:
       analytical_framework:
         - pattern_id: slogan_advocacy
           prompt_snippet: "统计论文中'应当''必须''需要完善'等表述数量..."
           ceiling: 60
           min_confidence: 0.65
       conclusion_consensus:
         - pattern_id: mechanical_application
           prompt_snippet: "检查结论是否采用立法-司法-执法-守法四分法..."
           ceiling: 55
           min_confidence: 0.65
   ```

3. 修改 `src/evaluation/concurrent_evaluator.py` 支持两阶段调用
   - 按上述"并发策略"实现：模型内串行（A→B），模型间并发
   - 对每个模型分别应用 ceiling，再按"多模型一致性决策规则"汇总
   - Stage A 和 Stage B 均调用 `log_call()`，保证审计链完整
   - 最终执行 `min(stage_b_score, ceiling)` 的代码在此模块

4. 修改 `prompt_builder.py`
   - 支持 `build_negative_pattern_prompt()`
   - 支持可选的 Stage A 摘要注入，但最终上限必须由代码应用

5. 修改 schema / validator
   - 新增 `NegativePatternResult` / `NegativePatternFlag`
   - `DimensionResult` 增加可选字段 `negative_pattern_triggered`
   - `normalize_dimension_result()` 负责校验 pattern_id 是否来自 YAML

### 预期效果

- 负样本均值：76.1 → ~73
- 识别率：44% → ~55%
- 正样本：不受影响（Stage A 不触发 → Stage B 正常运行）

### 验证方式

## Phase 2：Prompt 压缩与模块化

### 核心思路

在 Phase 1 证明代码层上限有效后，再压缩 prompt。避免同时修改架构和 prompt，导致效果无法归因。

### 具体步骤

1. **提取共享模板到 system_preamble**
   - output_contract、字数要求、JSON 格式说明等跨维度共享内容
   - 预计减少每维度 60-80 行

2. **简化评分标准表**
   - 保留锚定表（已验证有效）
   - 移除冗余的 anti_examples 和校准约束
   - 预计减少每维度 40-60 行

3. **将高风险 ceiling_rules 迁移到 Stage A 检测器**
   - 不是删除所有 ceiling_rules，而是把 v2.49 证明触发率为 0 的负面模式规则迁移到 Stage A
   - 原有已稳定工作的维度上限规则保留在维度 prompt 和 `normalize_dimension_result()`
   - 预计减少每维度 30-50 行

4. **修改 prompt_builder.py**
   - 支持 system_preamble + dimension_prompt + paper_content 的三段式组装

### 预期效果

- 负样本均值：~73 → ~72（边际改善有限，因为 Phase 1 已用代码层 ceiling 解决了 prompt 被忽略的问题）
- 识别率：~55% → ~58%
- 正样本：不受影响（评分逻辑不变，只是 prompt 更精简）
- **主要收益是工程层面**：prompt 可维护性提升、token 消耗降低、为 Phase 3 校准锚点腾出 prompt 空间

## Phase 3：校准锚点与负面示例

### 核心思路

用专家意见抽象出评分校准锚点，但生产 prompt 中不直接写入“某论文应得多少分”的样本特定结论，降低过拟合风险。

### 具体步骤

1. **为每个维度创建 2-3 个负面评分示例**
   - 从专家意见提取具体描述
   - 改写为抽象模式："当论文表现为[模式]，且缺少[可观察补救信号]时，预期得分区间为[范围]"
   - 专家意见原文只作为内部校准来源，不作为生产 prompt 的单篇记忆锚

2. **添加分数分布护栏**
   - 后处理检查：如果 `final_score > 80` 且 Stage A 命中高严重度负面模式，标记为可疑
   - 如果所有核心维度都 > 80 但 Stage A 命中多个负面模式，触发评价层复核
   - 触发人工复核

3. **在 Stage A 检测器中加入校准示例**
   - 让 AI 对照具体示例判断是否触发负面模式
   - 示例应覆盖触发与不触发两类，避免模型把相似主题全部误判为负面

### 预期效果

- 负样本均值：~70 → ~68
- 识别率：~65% → ~70%

## Phase 4：Autoresearch 自动迭代优化

### 核心思路

用 autoresearch 自动优化 Stage A 检测器的 prompt 和阈值参数。

### 为什么适合 autoresearch

- ✅ 有明确的机械化指标（discrimination_score）
- ✅ 修改范围有界（只改 YAML 中的 negative_patterns 区块）
- ✅ 有自动验证命令（batch_discrimination_test.py）
- ✅ 原子化修改 + 自动回滚

### 具体步骤

1. **创建 `scripts/batch_discrimination_test.py`**
   ```python
   # 快速模式：1 正样本 + 3 负样本，~5 分钟
   # 完整模式：3 正样本 + 10 负样本，~20-40 分钟
   # 所有 avg 均基于 final_score，不基于 legacy weighted_total
   discrimination_score = (
       (positive_final_avg - negative_final_avg)       # 量级 ~15-25，主要驱动力
       + 10 * negative_below_75_ratio                  # 量级 0-10，奖励识别率
       - penalty_for_positive_drop                     # 阶梯惩罚，见下方
       - 5 * positive_pattern_false_positive_rate      # 量级 0-5，惩罚误报
       - 2 * critical_std_count                        # 量级 0-6，惩罚不稳定
   )

   # 正样本保护：阶梯式惩罚（避免过度保守）
   # < 85 轻罚，< 80 重罚，< 75 极重罚
   if positive_final_avg >= 85:
       penalty_for_positive_drop = 0
   elif positive_final_avg >= 80:
       penalty_for_positive_drop = (85 - positive_final_avg) * 2   # 最多 10
   elif positive_final_avg >= 75:
       penalty_for_positive_drop = 10 + (80 - positive_final_avg) * 5  # 10-35
   else:
       penalty_for_positive_drop = 35 + (75 - positive_final_avg) * 10  # 极重罚
   ```

2. **配置 autoresearch**
   ```
   /autoresearch
   Goal: 最大化正负样本区分度
   Scope: configs/frameworks/law-v2.51-*.yaml (negative_patterns 区块)
   Metric: discrimination_score (higher is better)
   Verify: .venv/bin/python scripts/batch_discrimination_test.py --quick
   Guard: positive_final_avg > 85
   Guard: positive_pattern_false_positive_rate <= 0.10
   Guard: no single positive sample final_score drop > 5
   Iterations: 30
   ```

3. **每次迭代修改一个元素**
   - 一个 pattern 的描述文本
   - 一个 ceiling 阈值
   - 一个检测条件的量化标准
   - 禁止同时修改多个维度或多个 pattern，避免无法归因

4. **人工审查点**
   - 每 10 次迭代审查一次 pattern 命中证据，而不只看总分
   - 如果分数改善但 evidence quote 不支持 pattern，回滚该迭代

### 预期效果

- 负样本均值：~68 → ~65
- 识别率：~70% → ~75%
- 正负差距：~23 → ~26

## Phase 5：交叉验证与生产部署

### 具体步骤

1. **校准/回归集检查**
   - 先用 `raw/calibration-regression/` 确认正样本和既有判断没有被破坏
   - 只允许修复明显的契约、字段或执行错误；不得按单篇结果继续调 rubric

2. **冻结测试集验证**
   - 用 `raw/holdout-test/` 中的 4 篇论文验证泛化能力
   - 如果性能下降 > 5 分，诊断过拟合

3. **最终验证集**
   - 用 `raw/validation/` 8 篇一次性运行
   - 只记录结果和结论，不边跑边改

4. **多次运行稳定性测试**
   - 每篇论文运行 3-5 次
   - 确认负样本 std < 8，正样本 std < 5
   - 同时确认 Stage A pattern 命中结果稳定，不只看分数稳定

5. **生产部署**
   - 将验证通过的框架升级为生产推荐版本
   - 更新 CLAUDE.md
   - 归档优化历史

## 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 正样本分数下降 | 中 | 高 | Guard 条件：positive_final_avg > 85；每次迭代自动检查 |
| Stage A 误报导致正样本被硬压分 | 中 | 高 | Phase 0 dry-run；正样本误报率 guard；低置信度 pattern 只触发复核不压分 |
| 过拟合 10 篇负样本 | 高 | 中 | Phase 0/5 分离；pattern 描述用抽象标准；validation 一次性运行 |
| 只优化 weighted_total，偏离生产主分 | 中 | 高 | 所有 metric 改用 final_score；脚本显式输出 score_field |
| 两阶段延迟增加 | 中 | 低 | Stage A 只覆盖目标维度；短 prompt；后续可缓存 Stage A 结果 |
| API 成本增加 | 中 | 低 | Stage A 用同模型，每篇增加 2-3 次调用 |
| Autoresearch 发散 | 中 | 中 | 限制 30 次迭代；每 10 次人工审查；证据不支持则回滚 |

## 回退策略

### YAML `mode` 开关（一键回退）

`negative_patterns.mode` 支持三种值，生产环境可通过修改 YAML 一键切换，不需要改代码：

| mode | 行为 | 适用场景 |
|------|------|---------|
| `dry_run` | Stage A 正常运行并记录结果，但不应用 ceiling，Stage B 分数原样采用 | Phase 0 验证期；生产环境紧急回退 |
| `enforce` | Stage A 命中后代码层执行 `min()`，压分生效 | Phase 1+ 正常运行 |
| `disabled` | 完全跳过 Stage A 调用，等同于 v2.50.2 行为 | 彻底回退到旧版本 |

### 回退触发条件

出现以下任一情况时，立即切换到 `dry_run` 并诊断：

1. 任何正样本 `final_score` 下降 > 5 分（相对 Phase 0 基线）
2. 正样本 Stage A 误报率 > 15%（超过 guard 阈值）
3. 负样本分数反而上升（Stage A 干扰了 Stage B 的正常评分）
4. 多模型 Stage A 一致率 < 50%（检测器不稳定）

### 回退操作步骤

```bash
# 1. 修改 YAML 回退到 dry_run
sed -i '' 's/mode: enforce/mode: dry_run/' configs/frameworks/law-v2.51-*.yaml

# 2. 重新跑正样本确认恢复
.venv/bin/python scripts/run_convergence_test.py \
  --framework configs/frameworks/law-v2.51-20260515.yaml \
  --paper "raw/calibration-regression/蒋红珍..." \
  --output results/v2.51-test/rollback-verify.json \
  --score-field final_score

# 3. 诊断问题后修复，再切回 enforce
```
