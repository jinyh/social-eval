### 3.2 结构性差异(唯一需要决策的点)

**v0.14 新增第 3 阶段"自主知识体系信号校验"**(`law-ai-assisted-review-rules-v0.14-expert-edition.md:141-149, 200-222, 514-599`):

```
v0.13(3 阶段):     预检 → 六维评分 → 复核判断
v0.14(4 阶段):     预检 → 六维评分 → 【自主知识体系信号校验】 → 复核判断
```

**v0.14 对该阶段的明确要求**:
- 输出四类信号判断:`china_problem_centered`、`china_practice_explanation_attempted`、`external_theory_transformation`、`verifiable_concept_or_thesis` (`:729-762` 有完整 JSON 输出建议)
- 不是第七维度,不进入基础分公式
- 六维评分与信号结果矛盾 → 自动触发评价层复核(`:636-640`)
- 典型触发条件: 总分>70 但"中国问题中心性:否";总分<50 但四信号均为"是"等

**v2.42 的现状**:
- 在 `review_flags` 的 dimension-specific 枚举和 `expert_review_triggers` 中**隐性**提到了"china-problem"相关触发,但**没有独立的 `autonomous_knowledge_signals` 区块**。
- 用 `grep` 核验:v2.42 YAML 中不存在 `autonomous`、`signal`、`中国问题` 等关键字的结构化区块,规程要求的四类信号字段完全缺失。
- schema_v2.json **没有** `additionalProperties: false`(核验过 `:5-207`),所以在顶层新增一个区块不会被 schema 拒绝。

**这是 v2.42 相对 v0.14 唯一的实质性 gap**。

## 4. 建议(若后续实施)

### 4.1 建议做的改动(最小对齐)

在 v2.42 YAML 顶层新增 `autonomous_knowledge_signals` 区块,作为"规程文档化映射",即使代码暂未消费也无害:

```yaml
# 建议新增位置: v2.42 YAML 顶层,precheck 之后
autonomous_knowledge_signals:
  stage: 3   # 对应 v0.14 四阶段中的第 3 阶段
  name: 自主知识体系信号校验
  not_scoring_dimension: true   # 关键声明:不是第七维度,不进入基础分
  description: |
    独立检查步骤,整理文内可观察的自主知识体系信号;
    复用六维分析结果,不重复阅读论文;
    结果不进入基础分公式,只作为辅助信息和复核触发条件。
  signals:
    - key: china_problem_centered
      name_zh: 中国问题中心性
      values: [yes, no, partial, uncertain]
    - key: china_practice_explanation_attempted
      name_zh: 中国实践解释尝试
      values: [yes, no, partial, uncertain]
    - key: external_theory_transformation
      name_zh: 外部理论转化动作
      values: [sufficient, partial, insufficient, not_applicable, uncertain]
    - key: verifiable_concept_or_thesis
      name_zh: 可复核概念或命题
      values: [yes, no, partial, uncertain]
  contradiction_triggers:   # 对应 v0.14 §6.1.2"自主知识体系信号矛盾"
    - rule: total_high_but_no_china_problem
      condition: total_score > 70 AND (china_problem_centered == no OR china_practice_explanation_attempted == no)
    - rule: total_low_but_all_signals_yes
      condition: total_score < 50 AND all four signals == yes
    - rule: high_originality_but_no_verifiable_thesis
      condition: problem_originality >= 80 AND verifiable_concept_or_thesis == no
    - rule: slogan_heavy_but_no_legal_question
      condition: 大量使用"中国特色/自主知识体系/文化主体性"但无可定位法学问题
  output_contract:
    required_fields: [china_problem_centered, china_practice_explanation_attempted,
                      external_theory_transformation, verifiable_concept_or_thesis,
                      evidence_quotes, risks, triggers_review]
```

**版本标注建议**:修改后建议发布为 `law-v2.43-20260508.yaml`(遵循 CLAUDE.md 文档版本管理:功能新增→minor bump),保留 v2.42 为"对齐 v0.13 的最后一版"。

### 4.2 不要做的改动(反对 Harness 文档的建议)

**以下 Harness 文档建议都应拒绝(见第 5 节批判):**

| Harness 文档建议字段 | 为什么不应并入 framework YAML |
|---|---|
| `batch_run.parallel_workers` / `retry_policy` / `timeout_seconds` | 运行时基础设施配置,应放 `configs/runtime/` 或 CLI 参数,不同项目复用 framework 时不应绑死并发数。 |
| `filtering.high_score_threshold` / `priority_threshold` / `boundary_threshold` | 是"三阶段筛选"的项目级策略(v0.14 §1.1 说明 2000 篇筛选),不是法学评价框架本身的属性;不同项目/不同样本量阈值会变。 |
| `output_schema.dimensions`(重复列举) | 已通过 `dimensions[].key` 隐含,属冗余。 |
| `reliability.std_threshold` | **已存在**,字段名就叫 `std_threshold`,在 `src/knowledge/loader.py:16,42` 消费。Harness 文档说"需要新增"属事实错误。 |
| `output_schema.autonomous_knowledge_signals` | 输出契约应由 4.1 节的 `autonomous_knowledge_signals.output_contract` 承担,不需要再开一个 `output_schema` 顶层区。 |

## 5. 对 Harness 文档 `20260508_harness-engineering-analysis.md` 的批判性评价

用户已确认该文档是"探索草案,可批判"。逐条核对事实与设计取向:

### 5.1 正确且有价值的判断

- ✅ **"`configs/frameworks/` + 多模型并发 + 可靠性验证已构成评价框架迭代 harness"** —— 事实判断准确,与 `src/knowledge/loader.py` + `src/evaluation/orchestrator.py` + `src/reliability/calculator.py` 的代码现状吻合。
- ✅ **识别了四个真实 gap**: 大规模批量评价、预检门槛校准、三阶段候选池管理、分层抽样质检。这四件事都是 v0.14 §1.1 和附录 A/B 里明确要求、但当前代码没有的能力。
- ✅ **JSONL + SQLite 技术选型**适合批处理场景,合理。

### 5.2 事实错误(必须指出)

- ❌ **"建议新增 `reliability.std_threshold`"**
  - 真相:字段已存在,叫 `std_threshold`(顶层),见 `configs/frameworks/law-v2.42-20260507.yaml` 和 `src/knowledge/loader.py:16,42`,已在 `src/reliability/calculator.py:9,16` 用于置信度判断。
  - 这暴露文档作者**没有通读 `src/knowledge/loader.py` 和 schema_v2.json**。

- ❌ **"YAML 需要暴露并发数、重试、超时"**
  - 真相:当前代码 `concurrent_evaluator.py` 的并发是由"传入多少 provider 实例"决定的,重试/超时在 provider 层,不在 framework 层。把这些塞进 framework YAML 属于越界。

### 5.3 设计层面的问题

**问题 1:关注点混淆(最严重)**

Harness 文档把三类本应分离的配置塞进同一份 framework YAML:
1. **评价标准**(维度/权重/prompt/ceiling):属于"学科框架",版本化随学科演进。
2. **运行时参数**(并发数/重试/超时):属于"执行基础设施",跨框架复用。
3. **项目策略**(三阶段阈值/候选池规则):属于"具体筛选任务",同一个 framework 可以跑不同项目。

v0.14 规程本身就在 §1.1 说得很清楚:"候选规模不是预设配额,应根据分布、信号强度、专家质检动态确定"——这恰恰说明**不应把 threshold 硬编码到 framework YAML**。

**建议的正确拆分**:
```
configs/
  frameworks/        # 现状,只放学科评价标准
  runtime/           # 新增: 并发/重试/超时等基础设施参数
  projects/          # 新增: 三阶段筛选策略(如 three-journals-2000papers.yaml)
```

**问题 2:文档性 YAML 与可执行 YAML 混为一谈**

文档中 §6.2 给的 YAML 示例(高分/重点/边界阈值 75/65/60)是"规程文档化"的写法,但代码层**根本不读这些字段**。写进去不会报错,也不会生效——只是文档贴到了配置文件里,容易误导后来者以为"改这个阈值就能调系统行为"。

**问题 3:把"要做一套新 harness"包装成"改 YAML"**

文档 §4.1 清楚列出了需要**四个新 Python 脚本**(批量评价、预检校准、三阶段筛选、质量保障),但 §6 给出的影响清单却集中在 YAML 字段。这是**把工程量藏到了配置文件里**——真正的工作是写 Python(3-9 周),改 YAML 本身解决不了问题。

**问题 4:没有讨论与现有 `scripts/run_convergence_test.py` / autoresearch 的关系**

`agent-skills/autoresearch` 已经是一个自动迭代 harness 的实现,文档完全没提它,也没说明新提议的四个脚本是扩展、替换还是并存。这让读者难以判断落地路径。

### 5.4 建议修订方向(若文档作者继续迭代)

1. **更正事实错误**:`std_threshold` 已存在;重读 `loader.py` 和 schema_v2。
2. **明确拆分**:把"学科框架 YAML""运行时 YAML""项目策略 YAML"三者分开讨论。
3. **聚焦到 Python 脚本**:把 §6.2 的 YAML 示例替换为 Python 模块设计与数据模型(pydantic)。
4. **与 autoresearch 对接**:说清楚新 harness 是对 autoresearch 框架迭代能力的**横向扩展**(从"迭代框架"到"批量应用框架"),而不是平行方案。
5. **压缩范围**:四个新 harness 里,"大规模批量评价"是唯一真正紧迫的(2000 篇是硬需求);其余三个(预检校准/三阶段筛选/分层抽样)可以先用 Jupyter notebook 或一次性脚本,不需要独立 harness。

## 5.5 追加专题:v0.14 §7 输出规范是否应该进 YAML?

用户追问:"v0.14 中第 7 部分的输出规范,是否应该在 YAML 文件中?"

答案不是简单 yes/no,需要分层。先明确原则:

**判断准绳**:YAML 应承载"**契约**"(字段名/枚举/字数上限/required/optional,供模型遵循、供校验器校验);**不应**承载"**展示**"(人类可读的报告版式、UI 文案、HTML/Markdown 模板)。

### 5.5.1 v0.14 §7 四小节的分层处置

| v0.14 条款 | 性质 | v2.42 现状 | 应否进 YAML | 建议 |
|---|---|---|---|---|
| **§7.1 维度级输出**(原始分/分档/核心判断/证据/不足/硬约束) | 契约 | ✅ 已在 `output_contract` (`:255-317`),比 v0.14 还细(strengths/weaknesses/boundary_note) | **已在** | 不动 |
| **§7.1 字数限制**(每维 500/六维 3000) | 契约 | ✅ 已在 `output_constraints` (`:318-359`) | **已在** | 不动 |
| **§7.1 多模型统计**(均值/std/置信度标签) | 契约 | ⚠️ std 阈值在 `std_threshold`,但无输出字段声明 | **应进** | 新增 `multi_model_output_contract` 或并入聚合层契约 |
| **§7.1 最终报告聚合字段**(基础分/加分/上限/最终分/复核状态/复核层次/分流建议) | 契约 | ❌ 计算逻辑隐含在 `scoring_protocol`,但**没有声明聚合层输出字段** | **应进** | 新增 `aggregate_output_contract` |
| **§7.2 预检输出**(conclusion/enter_six_dim/triggered_signals 四信号/boundary_reasons/obviously_ineligible_reasons/requires_manual_confirmation) | 契约 | ⚠️ 只塞在 `precheck.prompt_template` 的自由文本里,**且字段不一致**(v2.42 prompt 输出 `status/issues/review_flags/recommendation`;v0.14 §7.2 要求 `conclusion/triggered_signals`) | **应进** | 新增 `precheck.output_contract`,并调整 prompt 对齐 |
| **§7.3 自主知识体系信号输出** | 契约 | ❌ 完全缺失 | **应进** | 已在第 4.1 节建议新增 |
| **§7.4 复核建议输出**(复核类型/层次/触发规则/关键问题/分歧/证据) | 契约 | ❌ 缺失 | **应进** | 新增 `review_report.output_contract` |
| v0.14 §7.2/7.3 里的 **JSON 示例**本身 | 展示 | - | **不进** | 用字段清单声明即可,不要把 JSON 样例整段拷进 YAML |
| 面向编辑部/专家的 **Markdown 报告模板** | 展示 | - | **不进** | 应在 `src/reporting/` 或 `templates/` 下单独存放 |

### 5.5.2 v2.42 的实际问题(核对原文后)

1. **`output_contract` 只覆盖"维度级"** (`law-v2.42-20260507.yaml:255-317`),但 v0.14 §7.1 最后还要求输出**聚合层字段**(基础分/加分/上限/最终分/复核状态/分流建议),这些字段**没有在 YAML 里被声明过**。
2. **预检输出契约是"隐形"的** (`:100-127`):`precheck.prompt_template` 让模型输出 `status/issues/evidence_quotes/review_flags/recommendation`,但这只是 prompt 里的自然语言要求——
   - 没有 schema 校验它
   - 字段名与 v0.14 §7.2 要求不一致(v0.14 用 `conclusion` + `triggered_signals`,v2.42 prompt 用 `status`)
   - 缺 `triggered_signals`(四信号)、`boundary_reasons`、`requires_manual_confirmation`
3. **复核报告和信号校验的输出字段完全缺失**。

### 5.5.3 具体建议(在第 4.1 建议之上扩展)

若后续发布 `law-v2.43-20260508.yaml`,建议 YAML 顶层结构扩充为:

```yaml
# 已有(保留不动)
output_contract:          # 维度级 - 模型直接输出 - 已完备
output_constraints:       # 字数 - 已完备

# 建议新增(都是声明字段清单 + 枚举 + 长度上限,不含 JSON 样例)
precheck:
  output_contract:        # 对应 v0.14 §7.2
    required_fields: [conclusion, enter_six_dimension_review,
                      triggered_signals, evidence_quotes,
                      boundary_reasons, obviously_ineligible_reasons,
                      requires_manual_confirmation]
    field_constraints:
      conclusion:
        allowed_values: [enter_six_dimension_review, boundary_review, obviously_ineligible]
      triggered_signals:
        required_keys: [involves_china_issues, has_legal_question,
                        china_practice_explanation_attempted,
                        theory_transformation_or_verifiable_thesis]
        value_enum: [yes, no, partial, uncertain]

autonomous_knowledge_signals:
  output_contract:        # 对应 v0.14 §7.3(第 4.1 节已建议)
    required_fields: [china_problem_centered, china_practice_explanation_attempted,
                      external_theory_transformation, verifiable_concept_or_thesis,
                      involves_special_chinese_institutional_issue,
                      evidence_quotes, risks, triggers_review]

aggregate_output_contract:   # 对应 v0.14 §7.1 最终报告部分
  required_fields: [precheck_conclusion, base_score, bonus_score,
                    conclusion_consensus_ceiling, final_score,
                    multi_model_stats, review_status, review_level,
                    triage_recommendation]
  field_constraints:
    review_status:
      allowed_values: [none, recommended, required]
    review_level:
      allowed_values: [precheck_level, evaluation_level, none]
    triage_recommendation:
      allowed_values: [enter_six_dim, boundary_with_review,
                       obviously_ineligible_manual_confirm,
                       pass_to_expert_deep_review]
    multi_model_stats:
      required_keys: [mean, std, confidence_label]
      confidence_label_enum: [high, medium, low, critical]

review_report:
  output_contract:        # 对应 v0.14 §7.4
    required_fields: [review_type, review_level, triggered_rules,
                      key_questions, model_divergence,
                      evidence_quotes, risk_notes]
```

### 5.5.4 落到代码的影响(提醒用户预判)

- **`precheck.output_contract` / `aggregate_output_contract` / `review_report.output_contract`** 进 YAML 后,需要 `src/evaluation/result_validator.py` 相应扩展校验逻辑,并让 `src/evaluation/precheck.py` 和 `src/evaluation/orchestrator.py` 在聚合阶段产出这些字段。这是**代码工作**,不在本轮范围。
- 若 YAML 写进去但代码不消费:仍然是"文档性对齐",零风险(见 4.3 节 `_normalize_framework_data` 只挑已知字段的机制)。但聚合层契约若有 schema 要求 required,需要同步更新 `schema_v2.json`,否则 loader 会报错。**温和做法**:先只写 `output_contract` 子结构,不把它们列入 schema 的 required,代码按需消费。

### 5.5.5 结论(一句话版本)

> v0.14 §7 **大部分字段契约应进 YAML**(预检/信号/聚合/复核四类 output_contract),**但 JSON 样例和面向人的报告模板不应进**;v2.42 的 `output_contract` 已覆盖维度级,**缺的是"聚合层 + 预检层 + 信号层 + 复核层"四份契约**,这四份值得补。
